# 0003 · 工具注册表是唯一的工具实现，MCP 服务暴露同一个注册表

## 状态

已采纳

## 背景

扁鹊的取证工具有两类调用方：进程内的取证子 Agent，以及经 MCP 接入的外部客户端（例如 Claude Code）。外部客户端需要认证与权限边界：每个客户端只能调用允许的工具，只能读取允许的命名空间。

如果 Agent 与 MCP 各有一套工具实现，参数校验、超时、重试、脱敏、证据持久化与调用记录都要写两遍，两边的行为会逐渐不一致，同一个工具在两种调用方下可能给出不同的结果或错误。

## 决定

1. 工具只在注册表（`backend/bianque/tools/registry.py`）里实现一次。声明包括名称、类别（`evidence` 或 `auxiliary`）、证据域与证据来源（取证工具）、`read_only`、pydantic 参数模型、超时与身份参数。注册在模块导入时发生，违反规则（非只读、名称不合规、类别与证据域不匹配等）时进程无法启动。
2. 取证工具在调查中调用时结果保存为证据。辅助工具（`knowledge_search`、`investigation_list`、`investigation_get_report`）只提供给 MCP 客户端，结果不是证据；MCP 客户端调用取证工具也不产生证据。
3. 执行器 `ToolExecutor.call`（`backend/bianque/tools/executor.py`）是工具调用的唯一入口：工具存在性、调用方权限、参数校验、命名空间范围、超时、重试、脱敏、证据持久化与调用记录都在这里。子 Agent 与 MCP 服务以不同的 `CallerScope` 调用同一个执行器。
4. 子 Agent 在进程内直接调用执行器，不经过 MCP 客户端。
5. MCP 服务用 MCP Python SDK 的 Streamable HTTP 传输，挂在后端同一进程的 `/mcp`，无状态并以 JSON 应答。工具定义从注册表生成，参数 schema 与 function calling 使用的是同一份。
6. 认证使用静态 Bearer 令牌：`BIANQUE_MCP_CLIENTS` 为每个客户端配置令牌的 SHA-256、允许的工具（支持 `fnmatch` 通配，启动时按注册表展开，匹配不到任何工具即启动失败）与允许的命名空间。`/mcp` 前的 ASGI 中间件校验令牌，失败返回 401。`list_tools` 只列出该客户端允许的工具；越权的调用与越界的命名空间由执行器拒绝，并以客户端名为 `caller` 写调用记录。

不采用的方案：

- 子 Agent 也经 MCP 客户端调用工具：同一进程内多一次 HTTP 往返与序列化，测试要启动服务，没有带来隔离。
- MCP 服务作为单独的进程：要重复加载注册表与配置，部署多一个组件，两边的版本可能不一致。
- SDK 的 OAuth 授权服务器：需要发布授权服务器元数据并实现完整的授权流程，超出当前的认证需求。需要时可以把中间件替换为 OAuth 资源服务器的令牌校验，执行器的权限检查不变。

## 后果

正面：

- Agent 与外部客户端看到的工具行为、错误、超时、重试与脱敏完全一致。
- 新增一个工具后，子 Agent 与 MCP 客户端同时可用，schema 只有一份。
- 所有调用（含被拒绝的）都在同一张调用记录表里，按 `agent` 与 `caller` 区分。
- 权限检查先于参数检查，调用方从无权调用的工具得不到参数信息。

负面：

- MCP 服务与后端共用一个进程，后端重启时 MCP 也短暂不可用；无状态设计使客户端在重启后可以直接继续请求。
- MCP 调用不属于任何调查，`pack` 后端下只能读 `BIANQUE_PACK_CASE` 指定的一个证据包。
- 客户端与令牌是静态配置，增删客户端或更换令牌需要修改 `BIANQUE_MCP_CLIENTS` 并重启后端。
- MCP Python SDK 的接口仍在演进，版本固定在 `backend/uv.lock`，升级需要单独验证。
