# 0001 · 取证由按证据域划分的子 Agent 并行执行

## 状态

已采纳

## 背景

一次 Kubernetes 告警的根因分析要从几类来源取证：集群对象的当前状态（Pod、事件、Deployment）、容器日志、变更记录（Deployment 修订历史与清单 Git 仓的提交）。三类来源的工具、参数与结果形态各不相同。

如果由一个 Agent 负责规划并调用全部工具，它的上下文里会同时堆积三类工具结果：日志可能有上百行，提交差异与对象快照也都是长文本，彼此挤占上下文，模型在后续步骤里更难定位相关证据。工具调用也只能串行进行，一轮取证的耗时是各类来源耗时之和。

另一方面，按角色拆分 Agent（规划者、批评者、报告者等）会让结论的产生路径变长，而结论是否可信取决于它能否回溯到证据，不取决于有多少个 Agent 参与讨论。

## 决定

1. 调查 Agent 负责计划、分派、证据充分性判断与报告。取证由三个取证子 Agent 完成，每个负责一个证据域：`kubernetes`、`logs`、`change`。证据域只在 `backend/bianque/agents/domains.py` 声明一次，计划的越界检查、分派、默认计划、充分性规则、证据门的置信度上限与子 Agent 的工具筛选都读这份声明。
2. 子 Agent 只能调用本证据域的取证工具，越域的调用由工具执行器拒绝并记录。子 Agent 以 ReAct 循环取证，最后以函数 `submit_findings` 提交发现，每条发现引用证据编号。子 Agent 不写报告；报告只由调查 Agent 生成，每条结论直接引用证据编号，而不是引用发现。
3. 同一轮计划里不同证据域的步骤用 LangGraph 的 `Send` 分派，在同一个 superstep 内并行执行；同一证据域的多个步骤在一个任务内依次执行。第一轮只允许 `kubernetes` 与 `logs`：变更归因需要先知道怀疑哪个对象与字段，`change` 从补充轮起参与。
4. 子 Agent 节点自己捕获异常，不向图抛出。LangGraph 中一个 `Send` 任务抛错会使整个 superstep 失败，其他子 Agent 的结果随之丢失。失败写入状态的失败列表，进入报告的缺失证据一节，并由证据门检查。例外是模型服务不可用之外的模型错误（录制响应缺失、请求被拒、脱敏残留），它们是配置或回放缺陷，使调查结束为 `failed`。
5. 不增加按角色拆分的 Agent。输出的校验由确定性的证据门完成，不由模型完成。

实现见 [`docs/architecture.md`](../architecture.md) 第 2、3 节。

## 后果

正面：

- 每个子 Agent 的上下文只包含告警、本步目标、本域之前的发现与本域的工具结果，不受其他证据域的长文本挤占。
- 一轮取证的耗时取决于最慢的证据域，而不是各证据域之和。
- 调用记录的 `agent` 字段区分 `investigation`、`kubernetes`、`logs`、`change`，界面按 Agent 分泳道展示流程图与调用时间线。
- 证据域是一张声明表，新增或替换证据域时改动集中在一处。

负面：

- 模型调用次数增加：每个子 Agent 的每个步骤都有自己的 ReAct 循环与一次提交发现的调用。
- 图的状态要合并多路结果。失败列表使用带合并函数的状态字段，并发追加；失败路径需要单独的测试用例（日志工具超时的回放用例）。
- 并行执行使完成顺序不确定。为保证录制响应能够匹配，提示词构造必须与完成顺序无关：结果按模型给出的顺序回填，证据与失败列表按编号排序，token 预算只在两轮之间检查，子 Agent 的保留标识符只取本证据域的证据。
- 不同子 Agent 可能取到同一对象。证据编号由工具名、身份参数与脱敏文本决定，同一内容在一次调查内只存一份。
