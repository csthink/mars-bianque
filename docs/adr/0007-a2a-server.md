# 0007 · 扁鹊作为 A2A 服务端：官方 SDK、JSON-RPC 绑定、任务状态由调查现算

## 状态

已采纳

## 背景

MCP 服务（[0003](0003-single-tool-registry-and-mcp.md)）把只读工具交给外部客户端，调查由客户端自己完成。另一类调用方是别的 Agent：它们手上有一条告警，想把整次调查交给扁鹊，拿回引用证据的报告。A2A 协议（Agent2Agent，规范 1.0）为 Agent 之间转交任务定义了 Agent Card、任务、状态更新与产出（Artifact）。

约束有四条。扁鹊的调查已经有状态正本（调查行与进度事件），任务状态不应另存一份。模型输出只能在通过证据门之后到达客户端，进度事件没有文本字段。修复建议的确认是登录的人的决定，记录只追加（[0002](0002-human-confirmation-records-only.md)）。经 A2A 发起的调查要与其他方式发起的调查发出相同的模型请求，录制回放与评测不受影响（[0005](0005-recorded-model-responses-for-eval.md)）。

## 决定

1. 只做服务端。扁鹊不调用别的 Agent：那需要出站访问与对方的凭据，调查本身也不需要。
2. 用官方 `a2a-sdk` 的服务端组件，挂在后端同一进程，只开 JSON-RPC 绑定（`POST /a2a`），Agent Card 在 `/.well-known/agent-card.json`。消息解析、协议版本检查、错误码与 SSE 由 SDK 负责；扁鹊实现 SDK 的请求处理接口与任务存储接口（`backend/bianque/a2a/`）。只有 `bianque.a2a` 导入 SDK，由 import-linter 契约保证。不开 gRPC 与 HTTP+JSON：每多一种绑定就多一套要测试的入口，而当前没有调用方需要它们。
3. 不使用 SDK 自带的请求处理器。它把运行中的任务放在进程内存里，经任务存储保存状态，只能订阅本进程正在运行的任务。扁鹊的任务状态在每次读取时由调查状态与最新进度事件算出，新表 `a2a_tasks` 只记录任务、上下文、调查与调用方的关联，或被拒的原因代码；进程重启后任务照常可读，中断的调查对应 `FAILED`。
4. 发起只接受一个 `data` 片段：演示形态是一条 Alertmanager 告警，与 webhook 走同一路径与指纹去重；回放形态是一个用例编号，按用例新开调查，这样没有集群也能完整走通 A2A。含自由文本等其他片段的消息返回内容类型不支持，不建任务；其余无法服务的请求建任务并直接结束为 `REJECTED`，状态消息以原因代码开头，不留下半开的任务。
5. 状态消息由代码按进度事件的类型与载荷生成，产出是已过证据门的正式报告或降级报告，与详情接口的报告相同，另附一段由代码生成的文本摘要。客户端拿不到模型的原始输出。
6. 修复建议不经 A2A 确认。任务在报告发布时结束为 `COMPLETED`，不进入 `INPUT_REQUIRED`；产出里带建议的编号、状态与详情页地址，确认在扁鹊页面上由登录的人完成。
7. 不做推送通知、取消、多轮消息与扩展 Agent Card。推送要扁鹊主动访问调用方给的地址并保管对方的凭据；流式加重新订阅已覆盖等待结果。调查不能中途取消。一个任务以一份报告结束，追问在扁鹊页面进行。
8. 认证与 MCP 相同：每个客户端一个 Bearer 令牌，配置里只存 SHA-256，令牌绑定命名空间，校验代码共用（`backend/bianque/auth/bearer.py`），两个服务互不导入。客户端只读得到自己发起的任务，别的客户端的任务与不存在的任务返回同一个错误。

不采用的方案：

- 按规范自己实现 JSON-RPC 处理：不加依赖，但兼容性要自己证明，出错面更大；端到端测试仍要用官方客户端才有说服力。
- 回放形态不开放 A2A 发起：CI 与没有集群的读者就只能用 `scripted` 模式验证，看不到真实录制下的完整流程。
- 用 `INPUT_REQUIRED` 把确认放进 A2A 任务：确认会脱离登录与只追加的记录，任务会停在等人的状态。

## 后果

正面：

- 别的 Agent 能把告警交给扁鹊并拿到引用证据的报告；进度只有事件类型与编号，报告不绕过证据门。
- 任务状态只有一个正本，重启后任务可查询；A2A 与 webhook、手动触发共用调查图、提示词与工具，录制响应照常命中，测试在 `scripted` 模式下比对请求键、在 `recorded` 模式下回放。
- 端到端测试用同一个官方 SDK 的客户端，证明与其他实现互通。

负面：

- 多一个发版很快的依赖，并带进 protobuf 与 google-api-core；版本固定在 `backend/uv.lock`，升级要重跑端到端测试。
- 对已结束的任务，`SubscribeToTask` 按规范返回不支持；断线期间任务结束的客户端要用 `GetTask` 取结果。
- 不流式的 `SendMessage` 默认等任务结束才返回，真实模型下会挂住一个请求几分钟；需要早返回时用 `returnImmediately` 或流式。
- 任务列表在内存里过滤与分页（状态是现算的），适合单个客户端任务不多的规模。
- 反向代理、`make replay`、`make demo` 与 Helm 都要为新入口加配置。
