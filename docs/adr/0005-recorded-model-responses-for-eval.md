# 0005 · CI 评测使用录制的真实模型响应，不用预写回答的桩模型

## 状态

已采纳

## 背景

CI 需要在没有外部模型服务、没有真实集群、没有网络的条件下跑通评测，指标包括根因是否判对、证据引用是否完整、证据门的首次通过率等。

常见做法是用桩模型满足断网要求。但桩模型的回答是预先写好的，用它算出的「根因判对率」只说明桩写对了，不反映 Agent 的提示词、工具设计与证据门在真实模型下的效果，这样的数字没有依据。

另一方面，每次 CI 都调用真实模型既需要密钥与网络，又会因为模型输出的随机性使结果不可复现。

## 决定

1. 模型网关支持三种模式，经同一个提供方接口接入，业务代码不知道当前模式：
   - `live`：OpenAI 兼容接口的真实模型，`temperature=0`。
   - `recorded`：按请求键查出事先用 `live` 模式录制的响应；查不到即报错，不回退到其他模式。
   - `scripted`：产品包里按 Agent 角色编写的规则响应器（`backend/bianque/agents/scripted_rules.py`），只能显式开启，用于单元测试、异常路径与端到端测试。
2. 请求键是「Agent 名称、规范化的消息列表、工具 schema、采样参数、模型名」的 SHA-256（`backend/bianque/llm/request.py`）。录制文件按用例存放在 `eval/recordings/<用例>/`，`recorded` 模式只查本调查用例的目录。录制清单 `eval/recordings/manifest.json` 记录模型名、`extra_body`、提示词文件与工具 schema 的哈希；回放时模型名与 `extra_body` 取自清单，显式配置与清单不一致时启动失败。
3. CI 评测使用 `recorded` 模式与证据包回放，检索使用事先计算的向量夹具，评测进程运行在没有外网的 Docker `internal` 网络里。
4. 提示词保持确定性：不含当前时间（回放时工具以证据包的录制时间为当前时间）；不含调查编号与会话编号；证据编号与修复建议编号由内容决定；证据、发现、失败与违规列表按编号排序；并发工具调用的结果按模型给出的顺序回填；工具错误只写类别与对象；token 预算只在两轮之间检查。测试在 `scripted` 模式下打乱子 Agent 的完成顺序，断言请求键不变。
5. 评测报告里的准确率数字只来自 `live` 或 `recorded` 模式，并注明模型名；`recorded` 的结果代表录制那一次 `live` 运行。
6. 重新录制（`make record`）先以 `live` 模式运行全部用例并录制，再以 `recorded` 模式回放，用 `bianque eval compare` 确认回放逐项重现了录制那次运行之后，才替换已提交的录制。

## 后果

正面：

- CI 在断网条件下复现真实模型的行为，准确率指标有实际含义，且每次运行结果相同。
- 录制文件保留完整的请求与响应，读者可以看到模型在每一步实际收到与返回了什么。
- 查不到即报错的规则使过期的录制在 CI 中直接失败，不会静默地用旧响应。
- `scripted` 模式让测试可以构造任意异常响应（被拒的报告、不存在的工具、缺字段的参数），覆盖证据门与降级路径。

负面：

- 改提示词、工具 schema 或换模型都会改变请求键，需要用真实模型重新录制，产生模型调用费用。
- 录制文件进入仓库，体积随用例与追问数量增长，并且要通过公开内容扫描。
- `recorded` 模式下追问的请求键包含会话历史，回放形态只能按录制顺序提问录制过的问题。
- `recorded` 的结果只代表一次运行，不代表同一模型每次都这样回答；统计稳定性需要用 `live` 模式多次运行。
- 确定性规则约束了提示词的写法与状态设计，新增的提示词内容必须遵守同样的排序与无时间规则。
