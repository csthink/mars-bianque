# 0002 · 修复建议由人确认或驳回，确认只记录、不执行

## 状态

已采纳

## 背景

调查报告除了根因，还包含修复建议，例如回滚某个提交、调整资源限制或修正探针路径。这些动作会改变集群或清单仓的状态。

自动执行修复需要一整套治理机制：谁有权批准、执行使用什么凭据、失败后如何回滚、执行结果如何核验。缺少其中任何一项，模型的一个错误判断就会直接变成对生产系统的写操作。扁鹊的重点是让根因判断可信并可回溯到证据，而不是执行变更。

同时，「Agent 提出、人来决定、决定留痕」这个环节本身有价值：确认记录是将来接入执行时的审批依据，而且它的数据结构不应在那时推翻重来。

## 决定

1. 正式报告发布时，每条修复建议写入 `suggestions` 表，编号由序号、动作、命令、风险等级与引用的内容哈希决定，之后不再修改。降级报告没有修复建议。
2. 每条建议标注风险等级 `read_only` 或 `change`。写类命令（`kubectl`、`oc`、`helm`、`git` 的写动词，模式在 `backend/bianque/gate/forbidden.py`）只允许出现在风险为 `change` 的建议的动作或命令里；在报告的其他字段、计划、判断、发现与追问回答中出现即被证据门的 `forbidden_actions` 拒绝。
3. 登录用户通过 `POST /api/investigations/{id}/suggestions/{sg}/decision` 确认或驳回一条建议，可附说明。处理只插入一行 `confirmations`，不运行任何工具，不调用数据库之外的任何系统。
4. `confirmations` 在数据库层面只追加：触发器 `confirmations_append_only` 拒绝 UPDATE 与 DELETE；`(investigation_id, suggestion_id)` 唯一约束保证每条建议只能决定一次，已决定的建议返回 409，并发的两次决定由该约束裁决。
5. 建议的状态（待确认、已确认、已驳回）由有无确认记录推出，不另存状态字段。
6. 系统中不存在写集群或写 Git 仓的代码路径：工具注册表拒绝 `read_only` 不为真的工具；Kubernetes 客户端只调用 `read_` 与 `list_` 开头的方法（CI 静态检查）；`git` 只允许 `log`、`show`、`rev-parse`；ServiceAccount 的 RBAC 只有 `get`、`list`、`watch`。

实现见 [`docs/architecture.md`](../architecture.md) 第 9 节。

## 后果

正面：

- 确认操作不可能改变集群或清单仓，模型的错误判断最多产生一条被驳回的建议。
- 确认记录不可篡改，确认人、决定、说明与时间都留在数据库里，可以作为审计记录与将来执行的审批依据。
- 「只能决定一次」与「只追加」由数据库约束与触发器保证，不依赖应用代码的正确性。
- 追问回答涉及处置时引用修复建议编号，而不是自己写命令，所有处置建议都经过同一份校验。

负面：

- 确认之后系统不会有任何动作，执行仍由人在系统之外完成。
- 决定写错时无法在系统内撤销或修改，只能由新的调查产生新的建议。
- 唯一约束与触发器也限制了测试数据的清理：端到端测试每次从空数据库启动。
